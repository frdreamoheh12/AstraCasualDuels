ASTRACASUALDUELS — COMPLETE DEVELOPMENT BLUEPRINT
=================================================

PLUGIN OVERVIEW
---------------
AstraCasualDuels is a configurable 1v1 duel plugin for Lifesteal Survival servers. Players challenge another player, configure a match through DeluxeMenus, wager in-game currency, and fight using their own equipment and inventory.

Core features:
- Player-to-player challenges.
- DeluxeMenus-based configuration interface.
- Custom battle maps.
- Custom duel levels.
- Manually registered duel themes.
- In-game currency wagering.
- Private bet amount input.
- Challenge acceptance system.
- Automatic countdown.
- Match start and end titles.
- Automatic winner payout.
- Player inventory preservation.
- Configurable sounds, messages and timings.

1. COMPLETE PLAYER WORKFLOW
---------------------------
1. Challenge a player:
   /duel PlayerName

   The plugin validates the target and creates a private duel setup session.

2. Main configuration menu:
   Automatically opens duel_setup.yml through DeluxeMenus.

   The challenger selects:
   - Map
   - Level
   - Theme
   - Bet amount

3. Select battle map:
   Default maps:
   - Desert
   - Iceland
   - Road
   - City

4. Select duel level:
   Default levels:
   - Beginner
   - Intermediate
   - Expert

5. Select theme:
   Themes are registered manually by the administrator. New themes must be addable through configuration without changing Java source code.

6. Enter wager amount:
   The player enters an amount through private chat input.
   Examples: 5m, 100k, 1000.
   Only the challenger sees the input prompt and their input.

7. Confirmation menu:
   Opens duel_confirm.yml and displays the selected opponent, map, level, theme and wager.

8. Send duel invitation:
   When the challenger confirms, the opponent receives an invitation containing the duel details and wager. The opponent must accept.

9. Prepare the match:
   Verify both players, balances, arena availability and match conditions. Assign both players to the selected arena.

10. Countdown:
    Configurable countdown: 5, 4, 3, 2, 1.
    Each number displays as a title with its configured vanilla Minecraft sound.

11. Fight begins:
    Display a configurable FIGHT BEGINS title and sound.
    Players fight using their own equipment and inventory.

12. Match completion:
    Detect the winner, handle wager payout, restore required player state and release the arena.

Create maps.yml. Maps must be administrator-defined, not hardcoded.

Example:

maps:
  Desert:
    enabled: true
    display-name: "&eDesert"
    world: "world"
    arena: "desert"

  Iceland:
    enabled: true
    display-name: "&bIceland"
    world: "world"
    arena: "iceland"

  Road:
    enabled: true
    display-name: "&7Road"
    world: "world"
    arena: "road"

  City:
    enabled: true
    display-name: "&6City"
    world: "world"
    arena: "city"

Each map should support:
- Enabled status
- Display name
- World
- Associated arena
- Description

Example arena configuration:

arenas:
  desert:
    map: Desert
    world: world
    spawn-1:
      x: 100
      y: 80
      z: 100
      yaw: 90
      pitch: 0
    spawn-2:
      x: 120
      y: 80
      z: 100
      yaw: -90
      pitch: 0

Allow administrators to create additional maps and arenas without changing Java source code. Each arena has two configurable spawn locations, including world, X, Y, Z, yaw and pitch.

6. BET INPUT SYSTEM
-------------------
When a player clicks the bet option:
1. Close the GUI.
2. Start a private chat-input session.
3. Send an input prompt exclusively to that player.
4. Accept shorthand amounts.
5. Validate the amount.
6. Store the wager.
7. Automatically reopen the main setup menu.

Supported input examples:

Input       Parsed amount
1000        1,000
100k        100,000
500k        500,000
1m          1,000,000
5m          5,000,000
10m         10,000,000

The parser must be case-insensitive and reject invalid, negative, zero and overflowing values.

Additional requirements:
- Input must never be broadcast to other players.
- Allow cancellation with a configurable keyword such as "cancel".
- Add a configurable input timeout.
- Handle player disconnects during input.
- Do not accept commands as wager amounts unless explicitly configured.

7. ECONOMY AND WAGERING
-----------------------
The wager is virtual server currency only.

Example:
- Player A stakes 5,000,000.
- Player B accepts and stakes 5,000,000.
- Total winner payout: 10,000,000.
- Winner receives both stakes; the loser's stake is transferred to the winner.

Implement an economy abstraction supporting Vault and an optional direct ExcellentEconomy integration where compatible.

Transaction rules:
- Do not withdraw money when a player merely opens a menu or starts configuring a challenge.
- Reserve both stakes only after the opponent accepts and the match is ready to begin.
- Do not allow either player to spend reserved money.
- If the duel is cancelled before combat starts, refund both players.
- Never pay out twice.
- Never charge the same player twice.
- Never allow negative balances.
- Handle failed withdrawals and deposits.
- Persist transaction state.
- Handle server shutdown and recovery.
- Handle offline winners and refunds safely.
- Make transaction processing idempotent.
- Do not silently lose currency if an economy operation fails.
- Do not construct unsafe console commands from untrusted player input.

9. MATCH MANAGEMENT
-------------------
Use a proper duel state manager.

States:
- CREATING: Challenger configures duel.
- PENDING: Waiting for opponent.
- ACCEPTED: Opponent accepted.
- PREPARING: Checking players and arena.
- COUNTDOWN: Countdown running.
- ACTIVE: Fight in progress.
- FINISHED: Match completed.
- CANCELLED: Match cancelled.

Detect:
- Player death.
- Player disconnect.
- Player leaving the assigned arena.
- Administrator cancellation.
- Server shutdown.
- Invalid arena or player state.

Do not declare a winner because of an unrelated damage event or an unfinished countdown.

Each match must have an isolated session and unique identifier. Prevent a player from participating in multiple simultaneous duels.

12. INVENTORY AND PLAYER PROTECTION
-----------------------------------
Players use their own grinded equipment. Do not automatically equip kits or replace their normal equipment.

Preserve player inventories, armor, offhand, experience and other required player state.

Implement reliable restoration on cancellation and normal match completion.

Use safe inventory snapshots and persistent recovery data where appropriate.

Never silently discard player items.

Make the protection system configurable.

Prevent exploits that duplicate equipment, let players escape match restrictions or avoid legitimate match results.

Explicitly define and test death-drop handling, disconnect handling, restart recovery and inventory restoration before production release.

13. MATCH COMPLETION
--------------------
When the match ends:
1. Determine the winner.
2. Mark the match as finished.
3. Prevent further combat.
4. Process the winner payout exactly once.
5. Restore the required player state.
6. Release the arena.
7. Send configurable winner and loser messages.
8. Clear the active duel session.

If the server crashes during an active match, recover the match and its escrow safely.

21. CRITICAL PRODUCTION CONSIDERATIONS
--------------------------------------
1. DeluxeMenus registration:
   Generating a menu file is not enough. Use the actual supported reload/registration workflow. Existing customizations must remain untouched.

2. Inventory protection:
   Players use their own grinded equipment. Inventory snapshots and restoration must be carefully designed. Death drops, disconnects and server crashes need explicit handling.

3. Wager security:
   Both stakes must be handled as one logical transaction. A failed second withdrawal must never leave the first player charged.

4. Duel recovery:
   SQLite must store enough match and escrow information to recover safely after a restart. A server crash must not accidentally award both players or lose reserved currency.

RECOMMENDED DEVELOPMENT ORDER
-----------------------------
First make /duel <player> open the actual DeluxeMenus configuration. Then finish selection and bet input. Next implement the challenge system. Finally add arenas, combat and economy transactions.

This order makes debugging easier and keeps GUI integration independent from the combat system.
